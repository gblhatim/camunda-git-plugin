Le plugin · positionnement

Ce que Gitflow demande à l'humain, et ce que le plugin fait à sa place

Gitflow est un modèle, pas un outil. Presque toutes ses règles reposent sur la discipline de celui qui tape les commandes — c'est exactement là que ça casse dans une équipe qui n'est pas composée de développeurs.

Gitflow — la règle standard Ce que fait le plugin
Deux branches longues develop/main, plus feature/ et hotfix/ Choix « tronc commun » ou « Gitflow » dans les réglages, écrit dans le .camunda-git.json partagé
Le point de départ d'une branche est une convention humaine Automatique — feature et bugfix partent de develop, hotfix part de main. Aucun choix à faire
Le nommage est une convention Imposé : feature/BDM-123456-slug, et affiché en clair dans l'interface
Release et hotfix doivent être fusionnés dans main et develop — deux commandes Une action « Intégrer » fait les deux merges --no-ff
L'oubli du back-merge est l'échec le plus classique, et le plus silencieux Détecté et signalé automatiquement
Le versioning repose sur la discipline humaine Version suggérée automatiquement, tag validé avant l'intégration
Les conflits se résolvent en git brut, avec des marqueurs dans le fichier Panneau de résolution dédié, au niveau fichier, jamais d'auto-résolution
Aucun contrôle sur qui touche main Mode développeur : l'auteur n'a pas accès aux commandes qui atteignent main
Le point clé Le plugin ne réinvente pas Gitflow. Il retire de la table les huit décisions qu'un auteur de méthode n'a aucune raison d'avoir à prendre.
