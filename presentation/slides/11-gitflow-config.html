Pilier 01 · configuration

Deux configurations, et une raison de les séparer

Analystes et développeurs travaillent dans le même dépôt. « D'où partent les features » ne peut pas être une supposition faite machine par machine — mais « quel dossier j'ai ouvert » ne regarde que moi.

Partagée .camunda-git.json — committée avec le projet
{ "branchModel": "gitflow", // ou "trunk" "baseBranch": "develop", "releaseBranch": "main", "branchPrefixes": { "feature": "feature/", "bugfix": "bugfix/", "hotfix": "hotfix/" }, "mergePolicy": "merge-request", "jiraHost": "…", "jiraProjectKey": "BDM" }
  • Écrite une fois, valable pour toute l'équipe.
  • Jamais générée automatiquement — créer ce fichier à l'ouverture d'un panneau salirait une copie de travail propre.
  • "trunk" = tronc commun, une version partagée. "gitflow" = version publiée séparée.
Locale ~/.camunda-git-plugin/config.json — par personne
{ "folder": "C:/methodes/univers-facturation", "tokens": { "gitlab": "…" }, "autoPull": false, "developerMode": false }
  • Dossier ouvert, jetons, auto-pull, mode développeur — propres à la machine.
  • Auto-pull désactivé par défaut, et jamais au démarrage du modeler.
  • Mode développeur désactivé par défaut, activé personne par personne.
Limitation connue et documentée : les jetons sont stockés en clair dans ce fichier local. C'est un choix assumé pour l'instant, pas un oubli — à traiter si le dépôt sort du poste de travail.
Le reste des garde-fous techniques — validation anti-traversal des chemins, routes mutantes en POST uniquement, jeton d'API régénéré à chaque lancement — vit dans le code, pas dans la configuration.
