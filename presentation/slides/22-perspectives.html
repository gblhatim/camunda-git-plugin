La suite

Ce qui est livré, ce qui reste, ce qui doit être confirmé

La distinction compte pour un comité : ce qui est déjà dans le dépôt n'est pas une perspective, et ce qui n'est pas vérifiable depuis ce dépôt ne doit pas être présenté comme acquis.

Déjà livré
  • Édition assistée par IA — conception aperçu puis application : rien n'est écrit sur disque sans accord, rien n'est jamais commité automatiquement.
  • Catalogue de patterns — approbation, boucle de relance, revue parallèle. Lus depuis le dossier du plugin, disponibles avant même qu'un projet soit configuré.
  • Recherche sémantique — sur tout le corpus de diagrammes, pas un grep de texte.
  • Résolution de conflit visuelle, y compris « combiner les deux ».
Ces quatre points sont souvent présentés comme des perspectives. Ils sont dans le dépôt, avec leurs tests.
Pistes identifiées
  • Créer une issue depuis le plugin — aujourd'hui la liste est consultable, la création se fait encore sur GitLab.
  • « Enregistrer mon travail » comme point d'entrée unique — la routine est déjà codée, elle mérite d'être mise en avant dans la démo.
  • Le mode « combiner les deux » comme argument différenciant fort — c'est ce qu'un client Git générique ne propose pas.
  • Chiffrement des jetons stockés localement.
Hors périmètre : les évolutions rFlow non liées à l'authoring Git/BPMN de ce plugin.
À reconfirmer
  • « 3 workers mockés sur 29 » — le chiffre vient du dépôt backend Airflow/rFlow.
  • Le statut de la contrainte SSL sur les appels aux API externes en local.
  • La configuration exacte des règles SonarQube — elle vit dans le dépôt CI/CD séparé.
  • Les chiffres de gain — objectifs ciblés issus du cadrage, à confronter aux premières méthodes réellement produites.
Aucun de ces quatre points n'est vérifiable depuis le dépôt du plugin. Les annoncer comme mesurés serait la seule vraie erreur possible dans cette présentation.
