Deux branches longues, trois branches courtes

Le modèle de branches n'est pas une convention affichée dans un wiki : il est écrit dans la configuration du projet et appliqué par le plugin. Le départ d'une branche n'est plus une décision humaine.

TypeTicketPart deFusionne dans
feature/* requisbranche courantebranche courante via MR revue
bugfix/* requisbranche courantebranche courante via MR revue
release/* —develop main + tag et develop
hotfix/* optionnel main — ce qui est live main et develop

Le nommage est imposé, pas suggéré

feature/BDM-123456-relance-client

Le numéro de ticket reste visible partout où la branche apparaît — Jira, journal de build, point quotidien. Il n'y a pas de branche sans ticket pour une feature ou un bugfix.

Deux exceptions assumées

  • hotfix part de main, pas de develop : on corrige ce qui est réellement en ligne.
  • Le ticket y est optionnel — exiger un ticket avant de corriger un incident live est une règle qu'on finit toujours par contourner.
Le dual merge en une seule action. Gitflow standard demande deux commandes ; l'oubli du retour vers develop est son échec le plus classique — et le plus silencieux. Ici, une action « Intégrer », et l'absence de back-merge est détectée automatiquement.
