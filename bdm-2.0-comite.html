Vue d'ensemble

Quatre piliers

BDM 2.0 ne se résume pas au plugin — il repose sur quatre piliers. Le plugin est ce qui les rend utilisables au quotidien, pas le sujet en lui-même.

Gitflow

Le modèle de branches : develop pour le quotidien, main pour la production, release/hotfix pour l'intégration contrôlée.

CI/CD

Le pipeline qui automatise build, tests et déploiement à chaque étape, sans intervention manuelle une fois le code poussé.

Environnements locaux

Exécuter une méthode avant même de la pousser sur Git, via Airflow+Camunda ou Spring Boot+mocks.

SonarQube

La porte de qualité qui valide une méthode avant sa mise en production.

Pilier 3 — environnements locaux

Environnement d'exécution local

Le détail complet des deux options — le survol sur les diagrammes précédents en donne un résumé rapide.

Airflow et Camunda tournent tous les deux en local : réplique complète de l'environnement réel, y compris les appels aux API externes utilisées par Airflow et l'équipe.

  • + Parité totale avec la production, aucun comportement mocké.
  • + Fonctionne désormais pour tous les workers, la contrainte de certificats SSL qui bloquait la communication avec les API externes est levée.
  • – Setup plus lourd : deux systèmes à faire tourner localement.

Camunda (Spring Boot embarqué) avec les workers en external task pattern mockés, et une base de données simulée — pas d'Airflow réel.

  • + Léger et rapide à lancer, rien à installer côté Airflow.
  • + Suffisant pour tester le comportement du workflow lui-même.
  • – Ne couvre que les workers déjà mockés : 3 sur 29 aujourd'hui.

La contrainte SSL qui limitait l'option A est résolue. Ce qui reste à étendre, c'est la couverture des workers mockés pour l'option B — priorisée par méthode plutôt qu'exhaustive avant tout déploiement.

Pilier 1

Gitflow — le modèle

Deux branches longues, trois types de branches courtes. Le plugin applique ce modèle, il ne l'invente pas. Survolez le diagramme pour le détail.

feature/* & bugfix/*

Le quotidien de l'auteur méthode. Partent de develop, nommage imposé feature/BDM-123456-slug — le ticket reste toujours visible dans le nom de la branche.

release/*

L'intégrateur regroupe une livraison. Dual merge vers main (tag de version) et develop (back-merge) en une seule action « Intégrer » — l'oubli du back-merge, échec classique de Gitflow, est détecté automatiquement.

hotfix/*

Correction urgente sur ce qui est déjà live. Part de main plutôt que de develop, suit le même dual merge que release/* — sans attendre le prochain cycle de livraison.

Pilier 2

CI/CD — le pipeline

Ce qui prenait 2 jours et 6 personnes en manuel se déclenche automatiquement à chaque push.

Deux instances du même pipeline : sur develop, il déploie en préproduction et le scan SonarQube est informatif. Sur main, il déploie en production — et n'est atteint que si la porte de qualité a été franchie.

Pilier 4

SonarQube — la porte de qualité

Un scan de la qualité du BPMN, pas de la logique métier — deux moments distincts, deux comportements distincts.

Sur develop (préproduction)

Le scan tourne à chaque push, mais n'empêche jamais le déploiement en préprod — il informe, il ne bloque pas.

À la promotion vers main

Le même résultat devient bloquant. Une méthode dont la qualité n'a pas été corrigée ne peut pas atteindre la production.

Ce qui est évalué

La structure du diagramme plutôt que le contenu métier — nommage des éléments, flux inutilisés ou orphelins, complexité des gateways, documentation minimale sur les tâches.

Le détail exact des règles reste à valider avec l'équipe SonarQube — ce qui est acté ici, c'est le principe : informatif tôt, bloquant tard.

Ce qui change

Ce que fait le plugin, concrètement

Le plugin ne remplace pas Gitflow, CI/CD ou SonarQube — il les rend utilisables au quotidien sans passer par un terminal. Fonctionnalités Git, plus un assistant IA et un catalogue de patterns, au même endroit.

Prise en main guidée

Checklist ordonnée (« My work ») : choisir le dossier, démarrer le suivi, se déclarer, créer le premier point de sauvegarde, connecter le serveur d'équipe si besoin. Aucune commande à taper.

Usage quotidien

Statut, diff, commit, push, pull en un clic. L'auteur voit l'état de ses fichiers et un bouton pour sauvegarder — jamais un terminal.

Diff visuel BPMN

Les éléments ajoutés ou modifiés sont surlignés directement sur le diagramme, les éléments supprimés listés à côté — pas de XML à lire.

Historique & traçabilité

Vue chronologique des versions d'une méthode : qui a changé quoi et quand, avec un historique complet — l'inverse du drive partagé sans mémoire.

Revue en Merge Request

Ouvrir une MR sur GitLab et suivre son état directement depuis le modeler, sans changer d'outil pour la revue.

Signaler un problème

Consulter la liste des issues GitLab ouvertes sur le dépôt directement depuis le plugin, sans changer d'outil. La création d'une issue se fait pour l'instant encore sur GitLab.

Release & hotfix

Version suggérée automatiquement ; une seule action « Intégrer » fait le double merge vers main et develop ; le retour oublié vers develop est détecté.

Résolution de conflit guidée

Un conflit ouvre un panneau dédié avec l'état exact de la fusion — jamais d'auto-résolution, jamais un fichier truffé de marqueurs bruts.

Garde-fous

Mode développeur qui sépare l'usage occasionnel des opérations sensibles (console, suppression forcée). En modèle Gitflow, jamais de push direct vers main — un mode « fusion directe » existe pour le modèle tronc commun en solo, avec avertissement explicite à l'écran.

Édition assistée par IA

Décrire un changement en langage naturel ; le modèle propose une nouvelle version du BPMN affichée en diff, jamais appliquée ni commitée sans validation explicite.

Catalogue de patterns prêts à l'emploi

Des diagrammes types (approbation, boucle de relance, revue parallèle...) livrés avec le plugin, à copier pour démarrer une méthode sans repartir de zéro.

Recherche sémantique

Retrouver une tâche, un assigné ou un processus appelé à travers tout le corpus de diagrammes du dépôt, en une recherche plutôt qu'en ouvrant chaque fichier.

Qui fait quoi — avant

Recette / non-régressionRIR
Déployer vers ProductionIR/AI

R Responsable (exécute) · A Approbateur (rend des comptes) · C Consulté (avis avant action) · I Informé (tenu au courant). Une même case R/A signifie qu'aucune séparation n'existe entre l'exécution et la responsabilité finale — c'est le symptôme principal du fonctionnement actuel.
