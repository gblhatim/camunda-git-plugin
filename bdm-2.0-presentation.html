BDM 2.0

Une méthode, ce sont deux livrables couplés : le workflow BPMN qui tourne sur rFlow et Camunda, et le ModOp qui le guide. BDM 2.0 change la façon dont l'équipe les produit — du drive partagé à Git, du déploiement manuel au pipeline automatisé.

Le changement

Ce qui change, en une ligne par sujet

BDM 2.0 ne change pas ce que produit l'équipe. Il change comment elle le produit : le support, la trace, le déploiement et la façon de travailler à plusieurs.

Avant le fonctionnement actuel
  • Drive partagé — un dossier « Univers », deux sous-dossiers, la concurrence gérée à la main avec son nom et la date.
  • Aucun historique — impossible de savoir qui a changé quoi, ni de revenir en arrière.
  • Déploiement manuel — deux uploads successifs sur rFlow, sans contrôle automatisé.
  • Conflits et écrasements — pas d'isolation entre auteurs sur l'environnement de test.
  • Pas d'environnement de développement — la première exécution réelle d'un processus a lieu sur l'environnement partagé.
Après BDM 2.0
  • Git — versioning complet, branches isolées par sujet de travail.
  • Historique Git complet — chaque changement daté, attribué, réversible.
  • Pipeline CI/CD — build, tests et déploiement déclenchés par un push.
  • Merge Request — la revue devient une étape du processus, pas une bonne volonté.
  • Environnement local complet — front/back rFlow et moteur Camunda sur le poste de l'auteur.
Le point important : c'est une limite de processus, pas des personnes qui l'exécutent aujourd'hui avec les moyens du bord.

Pilier 01 · Gitflow

Deux branches longues, trois branches courtes

Le modèle de branches n'est pas une convention affichée dans un wiki : il est écrit dans la configuration du projet et appliqué par le plugin. Le départ d'une branche n'est plus une décision humaine.

TypeTicketPart deFusionne dans
feature/* requisbranche courantebranche courante via MR revue
bugfix/* requisbranche courantebranche courante via MR revue
release/* —develop main + tag et develop
hotfix/* optionnel main — ce qui est live main et develop

Le nommage est imposé, pas suggéré

feature/BDM-123456-relance-client

Le numéro de ticket reste visible partout où la branche apparaît — Jira, journal de build, point quotidien. Il n'y a pas de branche sans ticket pour une feature ou un bugfix.

Deux exceptions assumées

  • hotfix part de main, pas de develop : on corrige ce qui est réellement en ligne.
  • Le ticket y est optionnel — exiger un ticket avant de corriger un incident live est une règle qu'on finit toujours par contourner.
Le dual merge en une seule action. Gitflow standard demande deux commandes ; l'oubli du retour vers develop est son échec le plus classique — et le plus silencieux. Ici, une action « Intégrer », et l'absence de back-merge est détectée automatiquement.

Pilier 01 · configuration

Deux configurations, et une raison de les séparer

Analystes et développeurs travaillent dans le même dépôt. « D'où partent les features » ne peut pas être une supposition faite machine par machine — mais « quel dossier j'ai ouvert » ne regarde que moi.

Partagée .camunda-git.json — committée avec le projet
{ "branchModel": "gitflow", // ou "trunk" "baseBranch": "develop", "releaseBranch": "main", "branchPrefixes": { "feature": "feature/", "bugfix": "bugfix/", "hotfix": "hotfix/" }, "mergePolicy": "merge-request", "jiraHost": "…", "jiraProjectKey": "BDM" }
  • Écrite une fois, valable pour toute l'équipe.
  • Jamais générée automatiquement — créer ce fichier à l'ouverture d'un panneau salirait une copie de travail propre.
  • "trunk" = tronc commun, une version partagée. "gitflow" = version publiée séparée.
Locale ~/.camunda-git-plugin/config.json — par personne
{ "folder": "C:/methodes/univers-facturation", "tokens": { "gitlab": "…" }, "autoPull": false, "developerMode": false }
  • Dossier ouvert, jetons, auto-pull, mode développeur — propres à la machine.
  • Auto-pull désactivé par défaut, et jamais au démarrage du modeler.
  • Mode développeur désactivé par défaut, activé personne par personne.
Limitation connue et documentée : les jetons sont stockés en clair dans ce fichier local. C'est un choix assumé pour l'instant, pas un oubli — à traiter si le dépôt sort du poste de travail.
Le reste des garde-fous techniques — validation anti-traversal des chemins, routes mutantes en POST uniquement, jeton d'API régénéré à chaque lancement — vit dans le code, pas dans la configuration.

Pilier 03 · environnements locaux

Exécuter une méthode avant de la pousser

C'est le pilier qui supprime la rupture la plus coûteuse du fonctionnement actuel : la première exécution réelle d'un processus n'a plus lieu sur un environnement partagé.

Option A

Airflow + Camunda en local

Une réplique complète de l'environnement réel, y compris les appels aux API externes utilisées par Airflow et l'équipe.

  • Parité totale avec la production — aucun comportement mocké, ce qui marche ici marche là-bas.
  • Fonctionne pour tous les workers — la contrainte de certificats SSL qui bloquait la communication avec les API externes est levée.
  • Setup plus lourd — deux systèmes à faire tourner localement sur le poste.

Quand la choisir

Dès qu'une méthode touche à un worker non mocké, ou qu'on veut valider un comportement d'intégration réel avant de pousser. C'est l'option de référence.

À reconfirmer avant le comité. Le statut exact de la levée de la contrainte SSL vit dans le dépôt backend Airflow/rFlow — il n'est pas vérifiable depuis le dépôt du plugin.
Option B

Spring Boot + workers mockés

Camunda embarqué dans Spring Boot, les workers en external task pattern mockés, base de données simulée. Pas d'Airflow réel.

  • Léger et rapide à lancer — rien à installer côté Airflow.
  • Suffisant pour tester le workflow lui-même — routage, passerelles, boucles, événements.
  • Ne couvre que les workers déjà mockés — 3 sur 29 aujourd'hui.

La couverture est priorisée, pas exhaustive

Les workers sont mockés méthode par méthode, selon ce dont les méthodes en cours ont réellement besoin — plutôt que de viser les 29 avant de commencer à s'en servir.

Pilier 04 · SonarQube

Informatif tôt, bloquant tard

Le scan porte sur la qualité du BPMN, pas sur la logique métier. Il ne dit pas si une méthode est juste — il dit si elle est lisible, maintenable et documentée par quelqu'un d'autre que son auteur.

Sur develop préproduction

Le scan tourne à chaque push, et n'empêche rien

Il informe l'auteur pendant qu'il travaille, au moment où corriger coûte le moins cher. Un déploiement en préproduction n'est jamais bloqué par la qualité.

À la promotion vers main production

Le même résultat devient bloquant

Une méthode dont la qualité détectée sur develop n'a pas été corrigée ne peut pas atteindre la production. C'est la porte de qualité du projet, et elle est portée par l'Intégrateur — pas par l'auteur.

Pourquoi ce découpage ? Une porte bloquante trop tôt se contourne : on désactive la règle, on marque en « faux positif », on pousse ailleurs. Bloquer au dernier moment garde le signal utile sans transformer le quotidien en course d'obstacles.

Ce qui est évalué — la structure, pas le métier

  • Nommage des éléments — une tâche appelée « Task_12 » ne dit rien à celui qui reprendra la méthode.
  • Flux inutilisés ou orphelins — des chemins qui ne mènent nulle part, vestiges d'une version précédente.
  • Complexité des passerelles — au-delà d'un certain nombre de branches, une passerelle devient illisible.
  • Documentation minimale sur les tâches — le lien avec le ModOp passe par là.
À valider avec l'équipe SonarQube. Le détail exact des règles et des seuils reste à arrêter — la configuration vit dans le dépôt CI/CD, pas dans celui du plugin. Le principe acté est celui-ci : informatif tôt, bloquant tard.

La démonstration de la porte de qualité se trouve sur la slide 12 — CI/CD : tentez une promotion sans avoir coché « qualité corrigée ».

Le plugin

Rendre les piliers utilisables sans terminal

Gitflow, la CI/CD et la porte de qualité existent avec ou sans le plugin. Ce que le plugin change, c'est qui peut s'en servir : un auteur de méthode qui n'ouvrira jamais une ligne de commande.

Conception et Git dans les mêmes panneaux

Statut, diff visuel, commit, push, Merge Request, résolution de conflit — au même endroit que le diagramme, dans le style d'un éditeur de code moderne. Pas d'aller-retour vers un autre outil.

Un vocabulaire qui n'est pas celui de git

« Point de sauvegarde » plutôt que commit, « sujet de travail » plutôt que branche, MODIFIÉ plutôt que M. Le nom technique reste accessible en infobulle pour ceux qui le veulent.

Des refus explicites

Pas de bouton pour supprimer un travail non commité, pas de force-push, pas de reset automatique, jamais de push direct vers main en modèle Gitflow. Ce que le plugin ne fait pas est aussi une décision de conception.

Construit avec Claude Code. Suite de tests couvrant fusion, MR, revue de MR, conflits, IA, catalogue, recherche et support — npm test.

Choix proposés — au niveau du fichier
Résultat

Choisissez une option à gauche.

« Combiner les deux » n'est proposé que si la fusion peut être garantie correcte. Le résultat est vérifié élément par élément après coup ; si la garantie n'est pas possible, l'option n'apparaît simplement pas. Correct, ou abstention — jamais une fusion potentiellement fausse.
  • Jamais d'auto-résolution silencieuse, jamais un fichier truffé de marqueurs bruts.
  • « Montrer les deux » rend les deux diagrammes côte à côte avant de trancher.
  • « Recommencer » (merge --abort) n'affecte jamais le travail déjà commité.
  • Gère aussi les rebase, cherry-pick et revert laissés en cours, avec l'inversion correcte de ours/theirs.

Le plugin · positionnement

Ce que Gitflow demande à l'humain, et ce que le plugin fait à sa place

Gitflow est un modèle, pas un outil. Presque toutes ses règles reposent sur la discipline de celui qui tape les commandes — c'est exactement là que ça casse dans une équipe qui n'est pas composée de développeurs.

Gitflow — la règle standard Ce que fait le plugin
Deux branches longues develop/main, plus feature/ et hotfix/ Choix « tronc commun » ou « Gitflow » dans les réglages, écrit dans le .camunda-git.json partagé
Le point de départ d'une branche est une convention humaine Automatique — feature et bugfix partent de develop, hotfix part de main. Aucun choix à faire
Le nommage est une convention Imposé : feature/BDM-123456-slug, et affiché en clair dans l'interface
Release et hotfix doivent être fusionnés dans main et develop — deux commandes Une action « Intégrer » fait les deux merges --no-ff
L'oubli du back-merge est l'échec le plus classique, et le plus silencieux Détecté et signalé automatiquement
Le versioning repose sur la discipline humaine Version suggérée automatiquement, tag validé avant l'intégration
Les conflits se résolvent en git brut, avec des marqueurs dans le fichier Panneau de résolution dédié, au niveau fichier, jamais d'auto-résolution
Aucun contrôle sur qui touche main Mode développeur : l'auteur n'a pas accès aux commandes qui atteignent main
Le point clé Le plugin ne réinvente pas Gitflow. Il retire de la table les huit décisions qu'un auteur de méthode n'a aucune raison d'avoir à prendre.

Le rôle qui n'existait pas : l'Intégrateur

Il porte la promotion vers main, le tag et le déploiement en production. C'est lui qui franchit — ou non — la porte de qualité. L'auteur d'une méthode ne peut plus la mettre en production seul.

Comparé à aujourd'hui

L'Admin Git/CI est approbateur sur le tag et le déploiement, mais n'exécute pas : il garantit que le pipeline fait ce qu'il prétend faire.

Organisation · gouvernance

Le risque qui n'est pas technique

La chaîne fonctionne. Le problème est ailleurs : la connaissance de son fonctionnement est concentrée sur deux points de défaillance, dont l'un est temporaire par nature.

Point 1

Hatim

Architecture, logique, débogage, évolution du pipeline. Tout ce qui n'est pas écrit ailleurs.

Point 2

Les interns

Implémentation — et temporaires par définition. Leur départ est daté, celui de la connaissance ne l'est pas.

Conséquence si le premier point disparaît : plus personne ne peut déboguer, maintenir ou faire évoluer BDM 2.0. Le pipeline continue de tourner — jusqu'à la première fois où il ne tourne plus.

Ce qui réduit réellement le risque

  • Documenter avant le départ des interns, pas après — ils sont les seuls à savoir pourquoi certaines choses sont faites ainsi.
  • Un cadre de gouvernance « à remplir » a été construit séparément pour Confluence.
  • La formation des futurs intégrateurs répartit la connaissance opérationnelle, pas la connaissance d'architecture.

La suite

Ce qui est livré, ce qui reste, ce qui doit être confirmé

La distinction compte pour un comité : ce qui est déjà dans le dépôt n'est pas une perspective, et ce qui n'est pas vérifiable depuis ce dépôt ne doit pas être présenté comme acquis.

Déjà livré
  • Édition assistée par IA — conception aperçu puis application : rien n'est écrit sur disque sans accord, rien n'est jamais commité automatiquement.
  • Catalogue de patterns — approbation, boucle de relance, revue parallèle. Lus depuis le dossier du plugin, disponibles avant même qu'un projet soit configuré.
  • Recherche sémantique — sur tout le corpus de diagrammes, pas un grep de texte.
  • Résolution de conflit visuelle, y compris « combiner les deux ».
Ces quatre points sont souvent présentés comme des perspectives. Ils sont dans le dépôt, avec leurs tests.
Pistes identifiées
  • Créer une issue depuis le plugin — aujourd'hui la liste est consultable, la création se fait encore sur GitLab.
  • « Enregistrer mon travail » comme point d'entrée unique — la routine est déjà codée, elle mérite d'être mise en avant dans la démo.
  • Le mode « combiner les deux » comme argument différenciant fort — c'est ce qu'un client Git générique ne propose pas.
  • Chiffrement des jetons stockés localement.
Hors périmètre : les évolutions rFlow non liées à l'authoring Git/BPMN de ce plugin.

Aucun de ces quatre points n'est vérifiable depuis le dépôt du plugin. Les annoncer comme mesurés serait la seule vraie erreur possible dans cette présentation.
